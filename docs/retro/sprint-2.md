## Start（下轮开始做）

1. **每天开工先在群里报"我今天改哪几个文件"**，一句话。本轮有两次两个人写同一块（#7 与 #4 同时实现 `QuestionCommandService`、#2 与 #4 同时改 Discovery 三个文件），都是因为没人知道对方在动什么。
2. **PR 标题里带上改动的文件或模块名**。现在只写"实现 XX 服务"，评审的人没法预判会不会冲突。
3. **合并顺序由 SM 统一排**：先小后大、先无冲突后冲突。本轮 #4 先合，直接让 #2 变成 dirty，本来排一下就能避免。

## Stop（下轮不要做）

1. 停止在旧分支上继续堆代码。分支落后 main 三小时以上就该 rebase，不要等冲突了才处理。
2. **停止在版本更替后重复认领同一个文件。** 动手前先看 `git log --oneline` 和开放的 PR，确认没有人在同一块上。本轮 Question 应用层的 7 个方法在 v3 里归 ④、v4 里归 ②，① 又实现了一遍，三次投入只落地一次。
3. **停止改了分工表却不发通知（本轮最大根因）。** v3 → v4 改过一次但只发了 v3，队友按旧版开工。上面第 2 条和 #7 都是它的下游后果，这条不解决，同类问题会重复发生。

## Continue（下轮继续保持）

1. **评审留 PR 评论**。#10 就是按 ③ ① 的意见修出来的，评论写在 PR 上比在群里说有效得多。
2. **同一个 PR 内的改动属于同一条链路**。#2 和 #4 各自横跨 S2 与 S3 两个上下文，评审时很难判断影响面——这条本轮做得不够，下轮按链路切。真正值得保持的是「一个 PR 只解决一个问题」。
3. **截图当场截**。CI 记录、PR 页面、看板状态都带时间，事后补不出来。
