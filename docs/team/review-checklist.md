# 团队代码评审清单 v1.0

> 维护人：xing-ding（Dev + QA） · 版本：v1.0 · 生效范围：全团队所有 PR
>
> 使用方式：评审他人 PR 时，逐项对照本清单，把**具体意见**写在 PR 评论里。
> 「至少 5 条实质性意见」指的是至少命中 5 个**不同维度**的、指向具体代码位置的评论，
> 而不是 5 句「Looks good to me」。
>
> 配套规范（分工方案「三条纪律」）：
> 1. 开工前 `git pull origin main`，做完立刻提 PR，别攒；
> 2. **不许改测试断言**——红了是没实现，不是测试错了；
> 3. 一个 PR 只做一件事，标题带 `feat:` / `fix:` / `test:` / `docs:` 前缀。

---

## 一、正确性（Correctness）

- [ ] **业务规则有据可依**：新增的校验分支能对上 `docs/错误码.md` 的错误码，或领域层的 javadoc 规则。
- [ ] **不变式被保护**：聚合的不变量在领域方法里校验，而不是散落在应用层或接口层。
- [ ] **边界值覆盖**：`0`、负数、超上限、空集合、`null` 的处理明确，没有"碰巧能跑"的路径。
- [ ] **异常类型正确**：状态冲突用 `ConflictException`，权限不足用 `ForbiddenException`，
      资源不存在用 `NotFoundException`，规则违反用 `BusinessRuleException`（见 `docs/错误码.md`）。
- [ ] **幂等性**：事件消费者、悬赏结算、投票撤销等"至少一次投递"路径必须可重复执行而结果不变。
- [ ] **并发安全**：计数器（score / answerCount / viewCount）用原子 SQL 增量维护，
      不做"读—改—写"（ADR-008）。

## 二、可读性（Readability）

- [ ] **命名达意**：方法名说明"做什么"，不暴露实现细节；领域术语与统一语言一致。
- [ ] **不做重复造轮子**：优先复用 `co-shared-kernel` 的 `Guard`、`Masking`、`UtcTime`、`PageRequest`。
- [ ] **方法不长**：一个方法只做一件事；出现 3 个以上分支或超过 40 行，考虑拆分。
- [ ] **注释解释"为什么"**：不复述代码。领域不变量、算法取舍、绕开坑的原因才写注释。
- [ ] **魔法值消除**：积分上限、天数、批大小等抽成常量或领域规则手册里的方法
      （如 `ReputationRulebook`），便于课堂讨论与参数调整。

## 三、可测性（Testability）

- [ ] **领域逻辑可脱离容器测试**：领域层是纯 Java，不依赖 Spring / JPA / Jackson（FF-1）。
- [ ] **新逻辑有测试**：新增的领域方法有对应单元测试；新增的应用编排有用例测试。
- [ ] **测试替身就位**：应用层测试用手写 Fake（参考 `QaTestFixtures`），不引入重量级 Mock 框架。
- [ ] **断言具体**：断言业务后果（事件载荷、增量数值、异常类型），不只断言"没抛异常"。
- [ ] **测试名说人话**：用 `@DisplayName` 写清场景，如「改投：增量按'新值 − 旧值'计算」。

## 四、安全（Security）

- [ ] **权限判定在服务端**：不在前端做权限控制；应用层用 `Actor` 显式传参，不从上下文隐式取。
- [ ] **越权访问被拒**：他人数据（声誉流水、积分）访问抛 `ForbiddenException`，不返回部分数据。
- [ ] **个人数据最小化**：积分字段仅本人可见；对外的 View 不含学号、邮箱等个人信息（ADR-003 / 个人信息保护）。
- [ ] **日志与审计脱敏**：日志/审计中的学号邮箱用 `Masking.account()` / `Masking.email()`。
- [ ] **注入面**：SQL 用参数绑定；用户输入不经字符串拼接进入 SQL；Markdown 输出在基础设施层做 XSS 净化。
- [ ] **CSRF 与会话**：写操作依赖双提交 Cookie 令牌；登录后轮换会话 ID。

## 五、性能（Performance）

- [ ] **无 N+1 查询**：批量场景用 `IdentityApi.findUsers` 等批量接口，不循环单查。
- [ ] **分页有上限**：`PageRequest` 的 size 上限 50；列表接口必须分页。
- [ ] **缓存有失效策略**：写操作后调用缓存失效（参考 `QuestionListCache.invalidateAll`）。
- [ ] **长事务被切分**：定时任务批量处理有上限（如 `BountyService.EXPIRE_BATCH_SIZE`）。
- [ ] **索引匹配查询**：查询条件命中数据库索引（如 `rep_account(reputation)`、`qa_question(deleted_at, created_at)`）。

## 六、风格（Style）

- [ ] **遵循现有范式**：构造器注入、依赖 `private final`、`Clock` 依赖置于最后。
- [ ] **时间取自 `clock.instant()`**：绝不直接调用 `Instant.now()`（否则不可测）。
- [ ] **事务边界正确**：写方法 `@Transactional`，只读方法 `@Transactional(readOnly = true)`；
      需与调用方同事务的方法用 `Propagation.MANDATORY`。
- [ ] **发事件在事务内**：事件与业务数据同事务落 outbox（ADR-002）。
- [ ] **包结构符合分层**：`api` / `domain` / `application` / `infrastructure` / `interfaces` 五层各司其职；
      跨上下文只经 `*-api` 包（FF-2）。
- [ ] **表名带上下文前缀**：`id_` / `qa_` / `rep_` / `dis_`（FF-6）。
- [ ] **格式一致**：4 空格缩进、行宽约 120；无行尾空格；文件以换行结尾。

## 七、评审时的红线（发现即打回）

| # | 红线 | 依据 |
|---|---|---|
| 1 | 修改了已有测试的断言以让测试变绿 | 分工方案「纪律 2」；CI 历史留档，属学术诚信范畴 |
| 2 | 把 `backend/pom.xml` 的 `domain.coverage.minimum` 调低来"通过"检查 | README 第 5 节；覆盖率门禁是适应度函数 |
| 3 | 直接向 `main` 分支推送 | 分支保护规则；main 需经 PR 评审合并 |
| 4 | 领域层引入 Spring / JPA / Jackson 依赖 | ArchUnit FF-1 |
| 5 | 跨上下文直接引用对方的 `domain` / `application` 包 | ArchUnit FF-2、FF-3 |
| 6 | 事件处理器未做幂等（重复投递会重复加分） | ADR-002；账本唯一键 `(event_id, user_id, reason)` |
| 7 | 绕过领域层直接在应用层改聚合内部状态 | 贫血模型；评分要点「聚合是否保护不变式」 |
| 8 | 一个 PR 混合多个不相关的改动 | 分工方案「纪律 3」 |
