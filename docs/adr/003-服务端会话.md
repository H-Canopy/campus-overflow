# ADR-003：认证采用 Redis 服务端会话而非 JWT

**状态**：已接受 ｜ **驱动特征**：安全性 ｜ **相关场景**：QS-06、QS-08

## 背景
校园场景需要教师/管理员能**立即**封禁违规账号、强制下线；同时前端是浏览器 SPA，存在 XSS 与 CSRF 两类威胁。

## 决策
使用 Spring Session + Redis 的服务端会话：会话 ID 放在 `HttpOnly`、`SameSite=Lax` 的 `SESSION` Cookie 中；
CSRF 采用双提交 Cookie（`XSRF-TOKEN` → `X-XSRF-TOKEN` 头）；登录成功后轮换会话 ID 防会话固定；
登录失败在 Redis 中按用户名限流（1 分钟 5 次）。

## 后果
- 正面：封禁即时生效（删除会话即可）；令牌不落在 JS 可读的位置，XSS 无法直接窃取；水平扩容时会话共享在 Redis。
- 负面：引入 Redis 作为可用性关键依赖（Redis 不可用则无法登录，但已登录用户的其他降级路径仍可读）。

## 被否决的替代方案
- **JWT（localStorage）**：无法即时失效，且 localStorage 里的令牌一旦 XSS 即被窃取。
- **JWT + 黑名单**：黑名单本身就需要 Redis，等于既付出了状态成本又失去了无状态的好处。
