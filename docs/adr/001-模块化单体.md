# ADR-001：采用模块化单体 + 六边形分层

**状态**：已接受 ｜ **驱动特征**：可演进性、可测试性、简单性（硬约束）

## 背景
团队是 5 人左右的本科生小组，只有 16 周、无运维人员、预算为零；同时课程希望学生真正理解限界上下文与演进式架构。
按架构量子分析，四个子域共享同一套用户与同一份数据、并且必须同步展示声誉与内容，静态耦合与动态耦合都指向**单一量子**。

## 决策
一个可部署单元内划分四个限界上下文，每个上下文再分 api / domain / application / infrastructure / interfaces 五层；
跨上下文只允许依赖对方的 `*-api` 模块或订阅其事件；数据库按表名前缀（`id_` `qa_` `rep_` `dis_`）隔离，禁止跨前缀 JOIN 与外键。

## 后果
- 正面：部署与调试成本极低；边界由 Maven 依赖图和 ArchUnit 测试强制，拆分服务时只需替换进程内事件总线；本地无需容器即可跑领域测试。
- 负面：物理隔离不足，开发者仍可能“绕过规则”（因此必须有 FF-1~FF-6 自动化检查）；单库成为共享资源，需要靠规范与代码评审守住。
- 演进路径：Discovery 是第一拆分候选（纯下游、只读投影、无强一致要求）。

## 被否决的替代方案
- **微服务**：加权评分最低（96/160），运维与调试成本远超团队能力，且没有任何独立伸缩或独立部署的真实需求。
- **分层单体**：最简单（87/160），但按技术分层会让四个子域的业务代码混在同一批包里，达不到课程的教学目标。
- **基于服务的架构**：评分最高（110/160），但需要 3 个以上部署单元与共享库版本管理，对 16 周的课程过重；其优点（边界清晰）已被模块化边界获得。
