# ADR-009：包结构与模块划分

**状态**：已接受 ｜ **驱动特征**：可维护性、可测试性、架构约束可验证 ｜ **相关场景**：FF-1 ~ FF-6

> 本决策是 [ADR-001 模块化单体](001-模块化单体.md) 在代码组织层面的落地细化。
> 它回答的问题是：六个限界上下文在 Maven 与包结构上具体怎么切、依赖怎么管、约束怎么自动化。
> Lab 4 要求记录的分模块决策，即此篇。

## 背景

四个限界上下文（Identity、Q&A、Reputation、Discovery）共享一个部署单元与一套数据库。
如果只按技术分层（controller / service / repository）分包，四个子域的业务代码会混在同一批包里，
改一个上下文要翻遍全项目，限界上下文就只剩文档上的说法。

同时，团队 5 人并行开发，需要一种机器能检查的边界，而不是靠口头约定。

## 决策

### 1. 以限界上下文做 Maven 模块的第一层切分

```
backend/
├── pom.xml                    父 POM：统一依赖版本、插件、质量门禁
├── co-shared-kernel/          共享内核：领域异常、Actor、事件契约、分页
├── co-identity/               身份与课程
├── co-qa/                     问答核心
├── co-reputation/             声誉与激励
├── co-discovery/              内容发现
└── co-bootstrap/              装配层：启动入口、安全链、发件箱中继
```

每个上下文模块内部再拆 5 个子模块，全项目共 27 个 Maven 模块：

```
co-qa/
├── co-qa-api/             发布语言：对外暴露的接口与事件契约
├── co-qa-domain/          领域层：聚合、值对象、仓储接口（零框架依赖）
├── co-qa-application/     应用层：用例编排、事务边界
├── co-qa-infrastructure/  基础设施：JPA 实体、适配器、Redis 缓存
└── co-qa-interfaces/      REST 控制器
```

### 2. 依赖方向只能向内

```
interfaces → application → domain
                  ↑
        infrastructure（实现 domain 定义的仓储接口）

api 被所有层引用，自身不依赖任何业务实现
```

- 领域层不依赖 Spring、JPA、Jackson——纯 Java，单元测试毫秒级
- 仓储接口定义在 domain，实现落在 infrastructure（依赖倒置）
- 跨上下文只允许依赖对方的 *-api 模块，禁止直接引用对方的 domain 或 infrastructure

### 3. 数据库按表名前缀隔离

| 上下文 | 前缀 |
|---|---|
| Identity | id_ |
| Q&A | qa_ |
| Reputation | rep_ |
| Discovery | dis_ |

禁止跨前缀 JOIN，也禁止外键跨上下文——需要的数据通过 api 查询或事件冗余。

### 4. 边界由 ArchUnit 自动验证

co-bootstrap 里的 ArchitectureTest 把上述规则写成断言，mvn test 就会执行：

| 规则 | 断言内容 |
|---|---|
| FF-1 | 领域层不得依赖 Spring / JPA / Jackson |
| FF-2 | 跨上下文只允许依赖 *-api |
| FF-3 | 模块之间不存在循环依赖 |
| FF-4 | 领域层行覆盖率 ≥ 70%（JaCoCo 门禁） |
| FF-5 | 实体表名必须带上下文前缀 |
| FF-6 | 控制器不得直接依赖基础设施实现 |

违反任何一条，CI 直接失败。

## 后果

**正面**

- 编译期就能发现跨上下文越界，不用等到 code review
- 领域层可脱离容器测试，112 个测试跑完约 30 秒
- 将来拆微服务时，只需替换进程内事件总线，模块边界不用动
- 新人看目录就知道代码该放哪一层

**负面**

- 27 个模块的 POM 维护成本，新增一个上下文要写 6 个 POM
- 跨上下文的简单查询也要绕 api，比直接 join 啰嗦
- ArchUnit 规则本身需要维护，规则写错会误伤正常代码

## 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 按技术分层分包（controller/service/repository 各一个包） | 四个子域的业务代码混在一起，限界上下文形同虚设，达不到课程考察目标 |
| 单模块 + 包级隔离 | 包之间没有编译期约束，靠自觉，实际一定会越界 |
| 一开始就拆微服务 | 4 个限界上下文各自部署，运维与联调成本远超 5 人团队 16 周的能力 |
| Gradle 多项目 | 团队已有 Maven 经验，且课程要求 Maven 多模块，切换无收益 |
