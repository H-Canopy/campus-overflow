# ADR-002：跨上下文集成使用事务性发件箱

**状态**：已接受 ｜ **驱动特征**：可演进性 ｜ **相关场景**：QS-04、R-2

## 背景
“采纳回答”一个动作要触发声誉记账、徽章、悬赏结算、搜索投影更新与通知。若在同一事务内同步完成，
Q&A 就会硬依赖三个下游上下文，响应时间与失败面一起放大；若直接用 `ApplicationEventPublisher` 异步发布，
则事务回滚后事件已经发出（或进程崩溃后事件永久丢失），一致性无法保证。

## 决策
业务写入与事件记录（`outbox_event` 表）在**同一个本地事务**中提交；`OutboxRelay` 以 `FOR UPDATE SKIP LOCKED` + 租约方式
认领未投递事件，按 id 顺序投递到进程内事件总线；投递语义为**至少一次**，消费端必须幂等
（声誉账本靠 `(event_id, user_id, reason)` 唯一键，投影靠 `processed_event` 表）。
失败事件指数退避重试，超过 10 次成为死信并由指标 `co_outbox_dead_letters` 告警。

## 后果
- 正面：不存在“业务成功但事件丢失”；下游故障不影响主流程；未来换成 Kafka/RabbitMQ 只需替换中继的投递目标。
- 负面：事件是**最终一致**的（演示时声誉会有数百毫秒延迟，需要向用户与评委解释）；多了一张表与一个后台任务；
  批内遇到失败会停止本批以保序，可能造成短暂积压。

## 被否决的替代方案
- 同步调用下游服务方法：耦合最强，且一个下游异常会让采纳整体失败。
- `@TransactionalEventListener(AFTER_COMMIT)`：进程崩溃时事件丢失，无重试与可观测性。
